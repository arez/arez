## Problem

Arez depends on Buildr, Ruby and Node-based documentation infrastructure even
though browser compilation already invokes Bazel through Ruby-generated temporary
workspaces. Contributors need one build graph that checks runtime libraries,
processors, generated code, browser examples, release artifacts and documentation.

## Required outcome

A clean checkout builds, tests, packages and previews every retained module with
Bazel and the documented Java/Bash/Python tools. Published libraries keep their
identities and equivalent behavior under JSpecify contracts. JVM and J2CL
consumers use the same binary/source archives prepared for Maven Central.

## Scope

In scope:
- Core, Arez processor, main integration tests, documentation examples, all four
  extras libraries, Persist core/processor/integration tests, and eight browser examples.
- Bazel layout/dependency generation, compiler policy, formatting, golden updates,
  hermeticity reporting, release artifacts, consumer targets, website, release
  orchestration, CI, coverage reporting and development documentation.
- Full GWT retirement, downstream-project-build removal, and removal of
  Ruby/Buildr/Yarn/Node project infrastructure.

Out of scope:
- Intentional runtime redesigns or features beyond changes required by the
  agreed nullability/compiler/build migration.
- Publishing a Maven release, creating a release tag or GitHub release, deploying
  the live site, changing downstream repositories, or merging a pull request.
- Publishing the example applications on the documentation site.
- New coverage percentages, a new golden framework, edits to reference
  repositories, or banning third-party transitive tools/annotations.

## Constraints

- Preserve intentional user changes. Current worktree was clean at planning entry.
- Runtime/generated bytecode and source compatibility remain Java 17. Running
  processors requires Java 21. Bazel execution tools use Java 25; J2CL's compiler
  explicitly uses Java 21. Document patched-JDK/type-annotation requirements.
  Owned processor classes also target Java 17; their shaded dependencies may
  require Java 21 but must not exceed that declared processor runtime baseline.
- Final builds use immutable remote dependency inputs, never local-path overrides.
  Local reference checkouts are evidence, not undeclared build inputs.
- Preserve API signatures, persisted data behavior and reactive behavior except
  for the confirmed GWT, nullability, source-distribution and toolchain cuts.
- Keep library identities under org.realityforge.arez:
  arez-core, arez-processor, arez-extras-dom, arez-extras-promise,
  arez-extras-spytools, arez-extras-testng, arez-persist-core,
  arez-persist-processor.
- Do not delete a retained regression case to make the build pass. Replace only
  tests of explicitly retired behavior with tests of its current contract.
- Implementation is sequential. Each task receives focused evidence and its own
  implementation/plan-state commit. The whole temporary plan is deleted only at
  verified closeout.

## Requirements

- R01: Every retained library, processor, example and JVM suite has a declared,
  runnable Bazel build/test path without requiring the old build.
- R02: Existing public identities and equivalent runtime/processor behavior are
  preserved subject to the explicit cuts; required semantic changes are documented.
- R03: Dependencies and Java toolchains are pinned and reproducible, with the
  agreed Java 17 output and Java 21 processor/J2CL requirements.
- R04: Owned and generated contracts use JSpecify. Interpretation honors marked
  and unmarked scopes, type-use position, generic substitution, inheritance and
  compiled declarations. Unspecified nullness is diagnosed where generation needs
  a definite answer. Legacy nullability annotations are ignored.
- R05: Owned compilations and valid generated output enforce Sting's strict
  Error Prone policy plus defaults and JSpecify-mode NullAway. Maintained Java is
  Palantir-formatted. Deliberate diagnostic inputs use plain javac.
- R06: Processor verification preserves both golden modes, exact emitted-file
  sets, diagnostics, warning promotion, multi-source/output/processor and
  multi-stage cases, and forked-javac formatter checks. Updates are focused and
  repeatable. Existing runtime invariant and integration event fixtures remain checked.
- R07: All eight artifacts produce deterministic binary, complete sources,
  Javadoc and POM outputs. Processors retain service registration and relocated
  self-contained runtime dependencies.
- R08: Public JVM targets and processor plugins consume those packaged artifacts;
  an isolated consumer proves they work without internal source targets or hidden
  processorpath dependencies.
- R09: Public J2CL targets for browser-capable libraries compile the published
  source archives, including generated Java and required JS resources; existing
  promise/spytools compilation coverage and Persist browser source compatibility remain.
- R10: All eight example applications have J2CL bootstrap, local runnable preview,
  and deterministic Chromium behavior tests in development and optimized
  production configurations.
- R11: The Java-generated website preserves valid authored content, navigation,
  document URLs, images/SVG includes, compiled-source snippets, API links and
  aggregate /api documentation. Local preview and local file/fragment checks work.
- R12: Release preparation, packaging/signing, Central upload, GitHub release and
  site-deployment commands replace the old orchestration. Local validation does
  not contact publishing services or alter remote repositories.
- R13: Build actions declare their tools/inputs and avoid network access.
  Ahab checks the full graph against reviewed evidence; justified browser test
  execution exceptions are narrow and documented.
- R14: One check entrypoint and CI run formatting, Buildifier, Ahab, builds,
  retained JVM tests, browser tests in both modes, release/consumer checks,
  site checks and JVM coverage reporting without new numerical gates.
- R15: The final checkout has no active Ruby/Buildr/Yarn/Node setup, downstream
  build module, GWT modules/compiler/API bootstrap support, or obsolete CI path.
  JS runtime companions and the J2CL-recognized GwtIncompatible marker remain.
- R16: Development/setup/release documentation and changelog match delivered
  behavior. The resolved processor-test deferral is removed after its conclusions
  are assigned durable owners and required documentation links are validated.
- R17: The reviewed plan controls local delivery, task evidence, full-scope
  verification, durable-knowledge promotion, implementation review and closeout.

  behavior. Changelog names the intentional user-facing cuts.

  local override. Artifact checks assert Java 17 bytecode for runtime artifacts
  and owned/generated classes, including owned processor classes. Shaded

  compatible; packaged processors run in a Java 21 isolated compiler and
  browser compilers use Java 21.
- AC04 (R04): Focused positive/negative/inherited/compiled/generic/array fixtures

  legacy annotations. Product code/goldens use JSpecify rather than legacy nullability.

## Technical decisions

- Use Bazel 9.3.0 and the reference rules_java 9.9.0 / buildifier_prebuilt
  10.0.1 / Ahab 0.4.0 / formatting rules 0.1.1 baselines, with checksum-pinned
  generated Maven repositories and explicit owning-package source lists.
- Final Java wrappers centrally own strict javac/Error Prone/NullAway options.
  Temporary baseline policy exists only to reach verified migration checkpoints;
  remove temporary opt-outs before the complete strict gate.
- Use the selected Proton module pin for both core and QA. The existing Sting
  0.40 processor emits legacy annotation contracts; integration tests/doc examples
  must consume compatible migrated Sting (reference revision
  fc89bc7c3f4450d3d1b75eaa58e63edfb37f1267), pinned remotely, as a test/example
  dependency. Do not modify Sting or Proton.
- Put effective-nullness interpretation in the Arez processor rather than
  modifying Proton: Proton preserves type-use annotations but does not resolve
  NullMarked/NullUnmarked defaults. Share only the minimum needed by existing
  Arez descriptors/generation. Persist preserves its skip-null storage behavior.
- Resolve defaults at the original declaration; an extending marked component
  does not mark an unmarked superclass. Preserve generic substitutions and
  nullable/NonNull type-variable meaning instead of assuming every bare T is
  nonnull. JSpecify canonical names must work on isolated processorpaths.
- Nullable arrays and nullable elements are separate. Legacy absence often
  represented permissive fixture setters/reference getters; mark those nullable
  explicitly rather than changing their behavior.
- Keep shared TestNG support compilation, selected golden families and separate
  plain-javac diagnostics/forked toolchain targets. Fixture data and generated
  resource expectations are explicit runfiles; architecture checks analyze
  declared bytecode archives or a test-local extraction, not a checkout target directory.
- Retain warning promotion and special compilation scenarios as single logical
  scenarios. Preserve Persist's additional Arez processor and output filtering.
- Public root JVM labels import the assembled release jars, with separate Arez
  and Persist processor plugins. Browser-capable J2CL labels compile assembled
  source archives; native JS/resources must be in those archives.
- Port only Rose's relevant J2CL/browser dependencies and patches, not its Node
  runner or app-specific test/profile/IDE machinery. JSpecify is a J2CL annotation
  import, not transpiled annotation sources with MODULE targets.
- Build examples using explicit JsInterop bootstrap plus Closure entry modules.
  Tests invoke the same application bootstrap as preview, use controlled browser
  APIs/network responses, and verify production defines as well as ADVANCED compilation.
  Each example/test source set also has an explicit strict Java 17 compile target
  against packaged JVM imports; J2CL compilation alone is not checker evidence.
- Port CommonMark/GFM rendering, compiled-source-jar snippet resolution, API link
  resolution, layout/navigation templates and local server. Adapt Arez's SVG
  include directive. Aggregate API documentation covers all eight published APIs,
  including currently omitted spytools, without changing existing API paths.
- Binary/source/javadoc archives use sorted entries, stable timestamps and
  unstamped metadata. Preserve both processor relocation namespaces, resources,
  required services and formatter runtime; processor POMs stay self-contained.
  Bytecode verification separates owned/generated classes from explicitly
  identified relocated processor dependencies, asserts Java 17 for the former
  and Java 21 compatibility for the latter, then executes both processors on
  Java 21. It must not exempt an entire processor archive.
- Ahab's baseline is reviewed evidence, not blanket approval of findings. Only
  necessary target-scoped browser execution/root-relative HTML exceptions are
  allowed; investigate other findings before updating it.
- CI verifies. Release commands remain explicit manual operations. The active
  implementation runs local previews/stubs only, never tags/uploads/deploys or
  downstream repository actions.

## Testing decisions

- Preserve an explicit inventory of retained test classes, provider rows, golden
  families and multi-stage cases before splitting execution. Source-file counts
  alone do not prove preserved coverage.
- Narrow task gates prove the active slice; aggregate parity, completed JSpecify,
  strict-policy and final gates are separate mandatory milestones.
- For the unavoidable wide refactor, T08-T13 is an expand/migrate/contract window:
  T08 migrates core contracts, T09 cuts processor APIs, T10-T11 migrate Arez
  scenarios, T12 migrates Persist, and T13 migrates remaining generated consumers.
  Known failures in not-yet-migrated suites are recorded, never reported as passing
  and never removed from the inventory. T13 restores the entire JVM gate.
- Strict checking then becomes complete in T14-T15, before packaging/browser work.
- Check nullable arrays/elements, marked/unmarked scope, explicit nullable/non-null
  type variables, inherited generic substitution, compiled base declarations,
  initializer/autodetection, setter checks, inverses, ReferenceId-derived contracts,
  disposal and collections. Legacy annotation presence must not influence output.
- Isolated artifact consumers exercise actual imports and packaged processors;
  J2CL consumers exercise actual source archives. Independent rebuild comparisons
  avoid mistaking cached outputs for reproducibility evidence.
- All eight browser applications run in both modes. Control permissions,
  geolocation, network, visibility, media queries and idle/time APIs where needed;
  avoid live-service or sleep-driven assertions.
  Example and browser-test Java are migrated to JSpecify in T20-T22, compiled
  through strict Java 17 targets and included in the T25/final check entrypoint.
- Site validation checks route identity, local fragments/assets, SVG includes,
  snippets including generated code, API links and local preview. External page
  links are not fetched as part of a hermetic build/check.
- Release preparation and command plumbing are exercised in disposable local
  copies/stub environments. A valid unsigned bundle is the local signing/publishing
  boundary; real credentials/signing/network publication remain user operations.
- The final task runs tools/check.sh from a clean dependency environment with no
  local module override and records actual commands/results, including both
  browser modes, nonempty coverage and all artifact/site/Ahab checks.
